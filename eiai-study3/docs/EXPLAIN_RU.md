# Что здесь лежит и как это работает

Путеводитель по репозиторию для человека без программирования. Состояние на 2 сентября
2026 года, коммит `28ae248`.

Технический аудит с таблицей «сделано / частично / нет» — в [`STATUS.md`](STATUS.md).
Этот файл отвечает на другой вопрос: *что вообще происходит и где что лежит*.

---

## А. Папки и файлы — по одной строке на каждый

### Верхний уровень

| Путь | Что это |
|---|---|
| `apps/study/` | Сам сайт, который видит участник. |
| `packages/schema/` | Описание всех данных: какие бывают события, какие у них поля. Единственный источник истины о формате. |
| `packages/fsm/` | Правила переходов между экранами и правило выбора регистра ответа по уверенности. |
| `packages/telemetry/` | Запись событий в браузере и отправка их на сервер. |
| `packages/stimuli/` | Загрузка замороженных текстов ответов ИИ и проверка, что они не менялись. |
| `services/ingest/` | Серверная часть приёма событий. **Написана, но никуда не развёрнута.** |
| `pipeline/` | Python-скрипты: генерация стимулов, проверки, анализ, отчёт. |
| `materials/` | Банк вопросов, замороженные тексты ответов, последовательность распределения, хеши. |
| `e2e/` | Роботы, которые проходят сайт в настоящем браузере как участники. |
| `docs/` | Спецификация, словарь данных, решения по архитектуре, этот файл. |
| `data/`, `paper/` | Результаты расчётов. Не хранятся в репозитории — пересоздаются командой. |
| `archive/` | Старые версии, оставленные для истории. |

### Скрипты в `pipeline/`

| Файл | Что делает |
|---|---|
| `_common.py` | Общие мелочи: поиск чисел в тексте на трёх языках, хеши, пути, загрузка ключей. |
| `generate.py` | Создаёт 144 текста ответов ИИ (12 вопросов × 3 языка × 4 варианта). |
| `providers.py` | Откуда берутся тексты: живая модель, заглушки без интернета, или написанное вручную. |
| `cell_cache.py` | Сохраняет каждый готовый текст сразу на диск, чтобы прерванный прогон ничего не терял. |
| `verify_equivalence.py` | Проверяет, что тёплая и нейтральная версии отличаются **только тоном**, а не содержанием. |
| `hash_manifest.py` | Считает «отпечатки» всех файлов стимулов; `--check` ловит любое изменение. |
| `verify_components.py` | Готовит бланки для двух оценщиков вслепую и считает согласие между ними (κ). |
| `allocation.py` | Заранее создаёт список назначений «кому какое условие», из зерна, по стратам. |
| `simulate.py` | Создаёт синтетических участников с заранее известным эффектом. |
| `replay.py` | Превращает журнал событий в таблицы для анализа. |
| `analysis.py` | Считает гипотезы H1–H5, байесов фактор; с флагом `--recover` проверяет сам себя. |
| `multiverse.py` | Прогоняет анализ 48 разумными способами и рисует кривую спецификаций. |
| `power.py` | Считает, сколько нужно участников. |
| `report.py` | Собирает всё в один документ с таблицами и графиком. |
| `verify_bridge.py` | Сверяет: то, что пишет симулятор, совпадает по форме с тем, что пишет настоящий сайт. |

## В. Где физически лежат данные и как они попадают к вам

Это самый важный раздел, и ответ сейчас неприятный.

### Шаг 1 — браузер участника (работает)

Каждое действие сразу записывается в хранилище внутри браузера участника — IndexedDB,
база данных `eiai-telemetry`. Файлы: `packages/telemetry/src/wal.ts`,
`packages/telemetry/src/recorder.ts`.

Запись происходит **до** попытки отправки. Поэтому обновление страницы, закрытие вкладки
или пропажа интернета ничего не теряют: при возвращении всё, что не ушло, лежит на месте
и отправляется заново.

### Шаг 2 — отправка на сервер (**работает локально, в облаке ещё не развёрнуто**)

Приложение отправляет пачки событий по адресу `/api/events`
(`apps/study/src/telemetry.ts`).

**Локально это теперь работает.** Команда `pnpm dev` поднимает и само приложение, и приём
событий по этому адресу: тот же самый серверный код, что будет работать в облаке, только
складывает события в файл `data/dev-events.jsonl`. Никакого аккаунта и базы для этого не
нужно. Проверить: `pnpm ingest:check --write`.

Весь путь «участник → сервер» покрыт тестами (`e2e/ingest.spec.ts`), включая обрыв связи
посреди задания: события ждут в браузере, потом доходят, и ни одно не дублируется.

**Чего ещё нет.** Проекта в облаке и базы данных. Пока их нет, ссылку участнику дать
некуда, и его данные останутся только на его устройстве. Пошаговая инструкция, как это
закрыть, — в `docs/DEPLOY.md`.

**Как убедиться, что после развёртывания всё действительно работает.** Это не праздный
вопрос: приложение устроено так, что переживает пропажу сервера молча. Если адрес окажется
неверным или база недоступна, участник ничего не заметит, и вы тоже — до момента, когда
данных не окажется. Поэтому есть отдельная команда:

```bash
node scripts/verify-ingest.mjs https://адрес-вашего-сайта --write
```

Она либо печатает «All checks passed», либо прямо говорит, что сломано. **Не набирайте
участников, пока она не проходит.**

### Шаг 3 — как данные попадут к вам

События накапливаются в одной таблице, в которую можно только **добавлять**: команды
изменения и удаления отозваны на уровне прав, плюс два триггера в базе, которые
останавливают такую попытку у кого угодно (`services/ingest/sql/001_events.sql`).
Выгрузка — один файл, где каждая строка это одно событие. Этот файл и есть вход для
анализа.

## Г. Как запустить анализ и где появится отчёт

Одна команда, из корня `eiai-study3`:

```bash
make paper
```

Она по очереди делает: синтетических участников → таблицы → гипотезы → 48 вариантов
анализа → документ.

Результат: **`paper/results.pdf`** — четыре страницы: размер выборки, средние WoA по
четырём ячейкам, H1–H5 с байесовым фактором, кривая спецификаций, проверка восстановления
параметров и все хеши.

Промежуточное: `data/tables/*.csv` (таблицы), `data/results.json` (все числа),
`data/multiverse/specification_curve.png` (график).

**Сейчас отчёт строится на синтетических участниках, а не на людях.** В шапке документа
это написано прямым текстом. Когда появятся настоящие данные, команда та же, код тот же —
меняется только входной файл.

## Д. Что делает каждая команда

### Команды `pnpm` (из `package.json`)

| Команда | Что делает |
|---|---|
| `pnpm verify` | Всё, что проверяет CI: типы, тесты, словарь данных, эквивалентность, манифест, распределение. Одна команда «всё ли цело». |
| `pnpm typecheck` | Проверяет типы, не запуская код. |
| `pnpm test` | 252 теста: обычные, свойствами (тысячи случайных входов), по модели автомата, на неизменность стимулов. |
| `pnpm test:py` | 12 тестов Python-части. |
| `pnpm test:watch` | То же, но перезапускается при правке файла. |
| `pnpm codegen` | Пересобирает словарь данных `docs/DATA_DICTIONARY.md` из описаний. |
| `pnpm codegen:check` | Проверяет, что словарь не отстал от описаний. |
| `pnpm stimuli:generate` | Создаёт тексты ответов ИИ (нужен ключ). |
| `pnpm stimuli:estimate` | Показывает, сколько будет стоить генерация, **до** траты. |
| `pnpm stimuli:equivalence` | Проверяет, что условия отличаются только тоном. |
| `pnpm stimuli:manifest` | Пересобирает список «отпечатков» стимулов. |
| `pnpm stimuli:check` | Эквивалентность + целостность вместе. |
| `pnpm coding:export` | Готовит бланки для двух оценщиков, вслепую. |
| `pnpm coding:score` | Считает согласие оценщиков (κ). |
| `pnpm allocation` | Создаёт последовательность назначений из зерна. |
| `pnpm allocation:check` | Проверяет, что файл назначений всё ещё соответствует зерну. |
| `pnpm sim` | Создаёт синтетических участников. |
| `pnpm replay` | Превращает журнал в таблицы. |
| `pnpm replay:check` | Доказывает, что таблицы пересобираются байт-в-байт. |
| `pnpm analysis` | Считает гипотезы. |
| `pnpm recover` | Симуляция → таблицы → проверка, что заложенные эффекты нашлись. |
| `pnpm multiverse` | 48 вариантов анализа и график. |
| `pnpm power` | Сколько нужно участников. |
| `pnpm e2e` | Роботы проходят сайт в настоящем браузере. |
| `pnpm e2e:ui` | То же, с окном, где видно каждый шаг. |
| `pnpm e2e:bots` | Три бота с разными стратегиями поведения. |
| `pnpm bridge` | Сверяет журнал симулятора с журналом настоящего сайта. |

### Команды `make`

| Команда | Что делает |
|---|---|
| `make install` | Ставит всё нужное, включая браузер для роботов. |
| `make verify` | То же, что `pnpm verify`. |
| `make sim` | Синтетические участники и проверка восстановления. |
| `make paper` | Всё до готового PDF. |
| `make repro` | Доказывает, что каждый создаваемый файл пересоздаётся одинаково. |
| `make clean` | Удаляет расчёты. `materials/` не трогает. |

### Python-скрипты напрямую

У каждого есть `--help`. Обычный порядок:
`allocation.py` → `generate.py` → `verify_equivalence.py` → `hash_manifest.py` →
*(сбор данных)* → `replay.py` → `analysis.py` → `multiverse.py` → `report.py`.

## Что стоит знать, даже если не читать остальное

1. **Данные сейчас никуда не уходят.** Серверная часть написана, но не развёрнута. До
   пилота это нужно закрыть.
2. **Тексты стимулов — заглушки.** Структура настоящая, содержание временное; в манифесте
   стоит `launch_ready: false`, и приложение это показывает.
3. **Правило остановки не запрограммировано.** Оно написано словами в отчёте, но никакая
   функция не отвечает «продолжать или можно останавливаться».
4. **Проверка манипуляции не считается.** Шкала теплоты собирается, но сравнение групп по
   ней не делается; шкала компетентности не считается вообще.
5. **Число страт нельзя изменить без правки кода** — в трёх местах.
6. **Что происходит с 385-м участником, не определено** — список назначений закончится.
